# Pedal CMS documentation

Documentation for the [Pedal CMS](https://github.com/PedalCMS/pedalcms) WordPress plugin, kept separate from the plugin so it never ships in the plugin zip.

| Folder | What it is | How it changes |
|---|---|---|
| `userguide/` | User guide (a hands-on course for site admins and editors), developer handbook and contributor guide. MkDocs + Material source. | Edited by hand. |
| `phpdocs/` | PHP API reference generated by phpDocumentor from the plugin source. | Rebuilt by this repository's Reference docs workflow. Do not edit. |
| `userguide/docs/developers/hooks-reference.md` | Every `pedalcms/...` action and filter, generated from the plugin source. | Rebuilt by the same workflow. Do not edit. |
| `tools/` | The generators: `build-reference.sh`, the hooks reference script and the phpDocumentor config and template. They read a checkout of the plugin. | Edited by hand. |

## Building the user guide

```bash
cd userguide
python3 -m venv .venv && . .venv/bin/activate
pip install -r requirements.txt
mkdocs serve            # live preview
mkdocs build --strict   # static site in userguide/site/
```

## Publishing

The docs are published at https://pedalcms.com/docs/. Deploy `userguide/site/` (the output of `mkdocs build --strict`) to `/docs/` and `phpdocs/` to `/docs/phpdocs/` on pedalcms.com.

`site_url` in `userguide/mkdocs.yml` must stay `https://pedalcms.com/docs/`. The handbook links to the API reference with the root-relative path `/docs/phpdocs/`, so both paths must move together if the location ever changes. Deployment is not automated yet.

## Reference docs workflow

The `.github/workflows/reference.yml` workflow keeps the generated pages current. Once a day it checks for a new full Pedal CMS release. When there is one, it checks out the plugin at that tag, runs `tools/build-reference.sh`, and opens a pull request on the branch `phpdocs/<tag>`. You can also run it by hand from **Actions > Reference docs > Run workflow**, optionally with a tag. Review the pull request and merge it. `.reference-tag` records the tag the pages were last built from.

The workflow also zips the PHP API reference and attaches it to that plugin release on GitHub as `pedalcms-api-docs-<tag>.zip`, so every release keeps an offline copy for its exact version. This step needs the `PLUGIN_RELEASE_TOKEN` secret below and is skipped without it. A manual run for the same tag uploads again and replaces the zip.

One-time setup in this repository:

- **Settings > Actions > General > Workflow permissions**: enable "Allow GitHub Actions to create and approve pull requests".
- Optional variable `PLUGIN_REPOSITORY`: the plugin repository as `owner/name`. Defaults to `PedalCMS/pedalcms`.
- Optional secret `PLUGIN_REPO_TOKEN`: only needed while the plugin repository is private. A fine-grained token with **Contents** set to read on the plugin repository.
- Optional secret `PLUGIN_RELEASE_TOKEN`: a fine-grained token with **Contents** set to read and write on the plugin repository, used only to upload the zip. Without it the zip step is skipped. The same token can also be stored as `PLUGIN_REPO_TOKEN` if the plugin repository is private.

Pull requests opened with the built-in token do not start other workflows.

### Previewing the generated pages locally

```bash
tools/build-reference.sh ../wp-content/plugins/pedalcms      # needs PHP 8.2 and Docker (or a phpdoc binary)
git restore phpdocs userguide/docs/developers/hooks-reference.md .reference-tag   # throw the preview away
```

See `userguide/docs/contributing/writing-docs.md` for the writing style and the full process.
